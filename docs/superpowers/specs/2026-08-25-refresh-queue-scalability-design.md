## 1. 背景 — 実測で判明した破綻

e-comi 本番（商品 926 件 / listing 2,729 件）で 2026-08-25 に実測した。

### 1-1. 供給側

| 指標 | 実測値 |
| --- | --- |
| 完了アクション（直近 24h） | **27,600 件** |
| うち実際に fetch できた件数 | **約 595 件** |
| **空振り率** | **97.8%** |
| 直接観測（18 分間）での内訳 | complete +867 に対し pending 減 **84 件**＝空振り率 **90%** |
| 失敗（failed） | **0 件** |

| 必要スループット | **95 件/時**（楽天+DMM の 1,803 listing を再取得しきい値 19h で 1 巡） |
| API レート制限の物理上限 | **6,872 件/時**（楽天 1.1s + DMM 1.0s） |

failed が 0 で pending も 197 件しかない。**API エラーでもキュー詰まりでもなく、消化したアクションの 9 割以上が何もせず完了している**のが実態である。

### 1-2. 処理の時間分布

過去 72 時間の `last_fetched_at` 1,788 件を「毎時何分か」で集計すると、**61% が毎時 29〜44 分に集中**する（ピーク :33）。一方で 13 分間まったく処理が進まない時間帯も観測された。

この偏りが商品の登録時刻に由来する可能性を検証し、否定した。

| 検証 | 結果 |
| --- | --- |
| 商品の作成時刻の分布 | 30-44 分は **26%**（最多は 45-59 分の 35%）。取得時刻の山と対応しない |
| 作成 3 日**より前**の商品の取得時刻 | 30-44 分が **66%** |
| 作成 3 日**以内**の商品の取得時刻 | 30-44 分が **24%**（00-14 分が 37%） |
| 同一商品での「作成の分」と「最終取得の分」の一致率 | **1%**（偶然の水準 1.7% を下回る） |

登録時刻が刻まれるなら新しい商品ほど偏るはずだが、実際は逆に**古い商品ほど山が鋭い**。周期は登録側ではなく再投入ループ側で生成されている。なお作成 3 日以内の商品が 00-14 分に寄るのは `PublishTrigger` による作成時 fetch が投稿時刻を刻むためで、こちらは想定どおりの挙動である。

### 1-3. sweep の投入量

06:28 に sweep の実行を直接観測した（pending 197 → 398）。

- 19 時間超の listing が **775 件**あったのに、sweep が積めたのは **201 件**
- `queue_depth_cap`(500) に対し走査開始時点の pending が 197 件で、**投入枠が 303 件しか残っていなかった**
- `Enqueuer::enqueueSweep()` は `as_schedule_single_action()` が unique 重複でスキップした場合も `++$this->depthMemo` するため、**実際には積まれなかった分も枠を消費する**

## 2. 根本原因

### 2-1. AS のバッチ claim と RateLimiter の即時再投入が噛み合っていない

Action Scheduler はジョブを**バッチ（既定 25 件）でまとめて claim し連続実行**する。一方 `RateLimiter` は account 単位で 1.0〜1.1 秒に 1 件しか通さず、**枠を取れなかったジョブを待たせずに即座に再投入**する（`ThrottledActionHandler::throttleWait()`）。バッチの実処理は数百 ms で終わるため、**1 バッチで fetch できるのは先頭の 1 件だけ**、残り 24 件は空振りして完了扱いになる。

`Enqueuer` の決定的スタガリング（同一 account の sweep ジョブを実効レート間隔ぶんずらして積む）はこれを避けるための仕掛けだが、**AS ランナー起動時に予定時刻を過ぎた pending がまとめて claim される**ため、積む時刻をずらしても実行時には同一バッチへ再集結して機能しない。

原設計（§7-2 #5）は「AS がバッチで複数アクションを走らせても account 単位のレートはプロセス跨ぎで厳守される」ことを保証の観点で書いているが、**厳守された結果として弾かれた側が空振りし続ける**ことは想定されていなかった。

### 2-2. 1 時間周期の thundering herd

`MAX_THROTTLE_WAITS`(30) に達したジョブは `time() + HOUR_IN_SECONDS` へ飛ばされる。この再投入に付く jitter は `RESCHEDULE_JITTER_SECONDS`(60 秒) のみで、**1 時間の周期に対して散らしが 2 桁小さい**。空振りしたジョブ群が毎時ほぼ同じ時刻に一斉に戻り、また激しく奪い合って 30 回に達し、また 1 時間後へ飛ぶ、という自己強化ループが固定化している。§1-2 の毎時 29〜44 分の山はこれである。

### 2-3. sweep が商品数に対して線形に重い

`QueueMaintenance::sweep()` は `posts_per_page => -1` で公開中の全商品を取得し、1 件ずつ `ProductRepository::find()` を呼ぶ。926 商品でも 1 回の WP-Cron 実行に収める必要があり、数万商品では実行時間・メモリの両面で完走できない。

### 2-4. 更新不要な商品を更新し続ける構造

公開中の商品は無期限に更新対象で、掲載記事が読まれなくなっても API を叩き続ける。供給側だけを直すと**無駄な更新も一緒に高速化する**（実 fetch が 595 件/日 → 1,803 件/日へ増える）ため、需要側の抑制が対で必要になる。

## 3. 設計方針

**商品数に依存しない構造にする**（特定の上限を目標にしない）。API レート制限から算出される理論上限は約 65,000 商品相当だが、**これは「実装が律速しなくなった場合の天井」であって、無条件に到達できる値ではない**。実際には次の制約が先に効く。

| 制約 | 効き始める規模 | 対処 |
| --- | --- | --- |
| `queue_depth_cap`（既定 500）× バッチサイズ（22） | **約 11,000 listing（≒5,600 商品）** | cap 到達時にカーソルを保持し、次の sweep で継続（§4-2）。cap は「1 巡あたりの投入上限」であって「更新できる商品数の上限」ではなくなる |
| sweep の走査時間 | 実行環境依存 | カーソル分割（§4-2） |
| API レート制限（6,872 件/時） | 約 65,000 商品 | 棚卸しで需要を削る（§5） |

つまり cap は**撤廃せず、意味を変える**。従来は「これ以上積めない＝取りこぼす」上限だったが、カーソル保持により「1 回の sweep で積む量の上限」となり、残りは次の sweep が引き継ぐ。これにより cap がスケールの天井にならない。

原設計の判断のうち、**実測が否定したものだけを改訂し、それ以外は維持する**。

| 原設計の判断 | 本 spec での扱い |
| --- | --- |
| §7-2 #2 ジョブ粒度＝per-listing | **改訂**。正常系はバッチ、異常系は per-listing（§4-1） |
| §7-2 #5 ワーカー＝AS 標準 | 維持 |
| §7-2 #4 優先度＝AS ネイティブ `$priority` | 維持 |
| §10-1 閲覧駆動リフレッシュ不採用 | **維持**（§5-1 で代替手段を採る） |
| §7-2 #10 multi-item API バッチ | 維持（後回し最適化のまま。スコープ外） |
| §3-5 CardRenderer の純粋レンダラ契約 | 維持 |

## 4. 供給側の設計

### 4-1. バッチジョブ＋per-listing フォールバック

per-listing 粒度を捨てず、**正常系と異常系で役割を分ける**。

```text
sweep → account 単位のバッチジョブを積む（1 ジョブ = N listing）
          ↓
       バッチハンドラ: ジョブ内でレート間隔を守りながら順次 fetch
          ↓ 成功 → 完了
          ↓ 失敗 → 既存の affilicard_refresh_listing（per-listing）へ落とす
                     → 既存の backoff / give-up / failed 可視化がそのまま効く
```

バッチ処理で消えるのは**正常系の空振り**だけである。per-listing 粒度が持っていた価値（dedup の同一性、account 別 group、指数バックオフ、give-up マーカー、failed の可視化、AS 標準 UI での個別 Cancel/Run、「失敗を再試行」）は**すべて異常系のための機構**であり、そのまま残る。異常系は少数なので、per-listing のまま扱っても枠の奪い合いは発生しない。

**新アクション**: `affilicard_refresh_batch`

| 項目 | 内容 |
| --- | --- |
| args | `{ account: string, items: [{post_id: int, platform: string}, ...] }` |
| group | `affilicard-{account}`（既存と同じ。AS 標準 UI の account フィルタが引き続き効く） |
| priority | sweep 由来＝20（既存の `PRIORITY_SWEEP` と同じ） |
| unique | true（同一 items 集合の二重投入を防ぐ） |

#### ハンドラの処理

1. pause ゲート（既存 `ThrottledActionHandler::run()` と同じ。温存のため自己再投入）
2. ジョブ開始時刻を記録し、**ジョブ期限**（開始時刻＋time limit −安全マージン）を確定する
3. `items` を順に処理
   - **残り時間を先に確認する。** 期限まで「レート待ち最大＋1 回の fetch 想定時間」を確保できない場合は、ここで**未処理分を新しいバッチジョブとして積み直して終了**する
   - `RateLimiter::tryAcquire()` で枠を取る。取れなければ次の枠が空くまで待つ（`usleep`）。**待機時間は残り時間を超えない上限でクランプ**し、クランプに掛かった場合は待たずに積み直して終了する
   - `ListingRefresher::refreshOne()` を呼ぶ
   - `SUCCESS` → 次へ
   - `TRANSIENT_FAILURE` → その listing を `affilicard_refresh_listing` へ enqueue（既存経路へフォールバック）
   - `TERMINAL_FAILURE` → give-up マーカーを立てて次へ（既存ロジックと同じ）
4. 完了

**期限チェックを待機の前に置くこと**が要件である。待機に入ってから期限を超えると、AS ランナーの時間予算を食い潰したうえに未処理分の積み直しも行われず、そのバッチの残りが失われる。

**HTTP タイムアウトを明示的に設定する**。Provider の fetch に接続タイムアウトと応答タイムアウトを与え、1 件の fetch が期限見積もりを超えて伸びないようにする。無指定だと WordPress の既定（5 秒）に依存し、環境によってはジョブ期限の前提が崩れる。

**ジョブ内で待つことについて**: 原設計は「AS ランナーを sleep で塞がない」ことを明示的な判断としていた（`RateLimiter` の docblock）。本 spec はこれを**バッチジョブの内側に限って**改める。理由は、待ち時間が 1.0〜1.1 秒と短く、かつ待たない場合のコスト（空振り 90%）が待つコストを大きく上回ることが実測で判明したためである。per-listing ジョブ側の挙動は**変更しない**（従来どおり再投入）。異常系は少数で、既存のリトライ機構との整合を優先する。

**バッチサイズ**: AS の `action_scheduler_queue_runner_time_limit`（既定 30 秒）に収まる件数を、account の実効レート間隔から算出する（例: 楽天 1.1s で安全マージン 25 秒なら 22 件）。フィルタで上書き可能にする。

#### 期待される効果

| | 現在 | 設計後（試算・バッチサイズ 22 件／失敗率 5% と仮定） |
| --- | --- | --- |
| 1 日のアクション数 | 27,600 | **約 170**（正常系 1,803÷22 ≒ 82 ＋ per-listing 90） |
| 空振り | 90〜98% | **0%**（正常系） |
| 1 時間周期の herd | 発生 | **消滅**（再投入が起きないため） |
| depth cap による sweep の絞り | 発生 | **消滅**（pending がバッチ数になるため） |

### 4-2. sweep の分割実行

`QueueMaintenance::sweep()` を**カーソル方式で分割**し、商品数に依存しないようにする。

- WP-Cron イベント `affilicard_refresh_all` は「sweep の開始ジョブを積む」だけにする
- sweep 自体を AS アクション（`affilicard_sweep`）とし、1 ジョブで M 商品を走査する
- 続きがあれば、最後に処理した post_id を**カーソルとして永続化**（option）してから次の sweep ジョブを積む
- 走査中に集まった対象 listing は、N 件たまるごとに `affilicard_refresh_batch` として積む
- 最後の商品まで到達したらカーソルを消し、完走時刻を記録する（§4-4）
- **`queue_depth_cap` に達した場合も、カーソルを保持して終了する**（取りこぼしにしない）。次の sweep がその位置から再開するため、cap は「1 回の sweep で積む量の上限」として働き、更新できる商品数の天井にはならない（§3）

これにより 1 回の実行時間が商品数に依存しなくなる。

**継続ジョブの投入失敗を握り潰さないこと**が要件である。継続ジョブが積まれないまま終了すると、**走査が途中で止まったまま次の WP-Cron まで再開せず**、カーソル以降の商品が丸ごと更新されない。カーソルを option に永続化しておけば、投入に失敗しても次回の sweep が途中から再開できる。投入失敗はログに残す。

### 4-3. `as_schedule_single_action()` の戻り値の扱い

`Enqueuer::enqueueSweep()` は戻り値を見ずに `++$this->depthMemo` している。戻り値 0 には**「unique 重複でスキップ」と「投入失敗」の 2 つの意味がある**ため、両者を区別して扱う。

| 戻り値 | 意味 | 扱い |
| --- | --- | --- |
| action ID（非 0） | 投入成功 | depthMemo を進める |
| 0（既存の pending と重複） | 既にキューにある＝作業は失われていない | depthMemo を**進めない**（枠を消費しない） |
| 0（投入失敗） | 作業が失われる | depthMemo を進めず、**ログに記録**する。sweep の継続ジョブの場合はカーソルを保持して次回再開に委ねる |

重複と失敗はいずれも 0 が返るため戻り値だけでは判別できない。判別には投入前後の状態（`as_has_scheduled_action()` など）を用いるか、少なくとも**「0 が返った＝正常にスキップされた」と決めつけない**実装にする。

### 4-4. cron 健全性の検出

現在の `CronDisabledNotice` は `GeneralSettings::isCronEnabled()`（プラグインの設定トグル）しか見ておらず、「トグルは ON なのに実際には動いていない」状態を検出できない。今回の実測でまさにその状態が起きていた。

- **最後に sweep が完走した時刻を option に記録**する。§4-2 でカーソル分割するため、「完走」＝**カーソルが最後の商品まで到達し、続きのジョブを積まずに終了したとき**と定義する（分割された途中のジョブでは記録しない）
- 管理画面（キューパネル）に「最後の掃引: N 時間前」を表示する
- 期待間隔（`refresh_interval_hours`）を大きく超えている場合は警告を出し、対処手順へ誘導する

**運用ドキュメントの整備**: [`docs/operations-refresh-queue.md`](../../operations-refresh-queue.md) の既存 cron セクションに追記する。

- WP-Cron のままで足りるか、サーバー cron へ移すべきかの判断基準
- `DISABLE_WP_CRON=true` にした場合、`wp action-scheduler run`（キュー実行）**に加えて** `wp cron event run --due-now`（掃引イベントの発火）も登録しないと継続更新が止まる、という落とし穴（原設計 §11 に記載済みの内容を利用者向けに再構成する）

**設定画面からこのページへの導線を張る**。現状はドキュメントが存在しても管理画面から辿れず、利用者が到達できない。

## 5. 需要側の設計（棚卸し）

### 5-1. 判定の基礎＝最終掲載日

**記事の公開・更新時に、その記事が参照している商品へ「最終掲載日」を記録する。** 一定期間これが更新されない商品を更新対象から外す。

閲覧駆動（§10-1 で不採用）と異なり、この方式は不採用理由をすべて回避する。

| §10-1 の不採用理由 | 本方式 |
| --- | --- |
| 毎閲覧の DB 書き込み負荷 | **発生しない**（記事の公開・更新時のみ） |
| 未認証書き込みパス | **存在しない**（管理操作のみ） |
| ページキャッシュ/CDN で発火しない | **影響を受けない**（描画と無関係） |
| CardRenderer の純粋レンダラ契約 | **触らない** |

GA4 等の外部分析基盤と連携する案も検討したが、**利用者の計測環境に依存する**ため汎用プラグインとして不適と判断し、採らない。本方式はプラグイン単体で完結する。

**記録の実装**: `PublishTrigger::syncPost()` が既に「記事本文から参照商品 ID を解決する」処理（`resolveProductIds()`）を持っているため、ここに記録処理を追加する。

**記録する値は「記事の公開日時」ではなく「記録時点の現在時刻（UTC）」とする。** 公開日時を使うと、過去日付の記事を後から編集した場合や予約投稿（`future` → `publish`）で未来日時が入る場合に、値が実態とずれる。判定したいのは「最後に掲載面へ手が入ったのはいつか」なので、イベント発生時刻が正しい。

**更新は単調増加とする。** 複数記事から参照される商品では、既存値より新しい場合のみ書き込む（既存値が新しければ何もしない）。イベント時刻を記録する以上、通常は常に増加するが、順不同の保存やクロックのずれで古い値が入る余地を残さないため、比較を明示する。

### 5-2. 判定式

```text
棚卸し対象 ⇔ ( 最終掲載日 ?? 棚卸し基準日 ) + stocktake_days × 86400 < 現在時刻
```

比較はすべて UTC epoch 秒で行う（`last_fetched_at` / `last_verified_at` が `gmdate('c')` で実 UTC を記録している既存方針に揃える。サイトのタイムゾーン設定に判定が左右されないようにするため）。

**`??`（null 合体）だけに頼らないこと。** 最終掲載日は null のほか、**空文字**（meta が存在するが値が空）や**形式不正**（パース不能な文字列）を取り得る。`??` は null しか捕まえないため、空文字がそのまま計算に流れると `strtotime()` が false を返し、判定が不定になる。共通の正規化処理を通し、**null・空文字・パース不能のいずれも「無効値」として棚卸し基準日にフォールバック**させる。この正規化は判定を行うすべての箇所（sweep・管理画面の表示・一覧の絞り込み）で共有する。

**状態を持たない。**「棚卸し済み」フラグは立てず、毎回この式で評価する。この性質は意図したものである。

- 期間を短く設定しすぎた場合、**設定を戻すだけで対象へ復帰する**（フラグ方式では「設定を戻したのに復活しない」という驚きが生まれる）
- フラグの整合性管理とマイグレーションが不要になる
- 「流入があるのに棚卸しされた記事」に対する、記事再保存以外の救済経路になる

期間を大きく延ばした瞬間に多数の商品が一斉に対象へ戻るが、バッチ化・スタガリング・depth cap が吸収するため実害にならない。

### 5-3. 棚卸し基準日（既存商品の初期値）

既存商品には最終掲載日が無い。本機能を含むバージョンへの移行時に「棚卸し基準日」を option へ記録し、最終掲載日が無効な商品はこれを代用する。

- **記録は `register_activation_hook` ではなく、バージョン付きのアップグレードルーチンで行う。** WordPress の自動更新や管理画面からのプラグイン更新では activation hook が実行されず、**プラグインを有効にしたまま更新したサイトでは基準日が永久に記録されない**（＝棚卸しが一切発動しない）。既存の `META_SCHEMA_VERSION` / `SchemaVersion` と同種の、保存済みバージョンと現在バージョンを比較して差分処理を走らせる仕組みに載せる
- 記録は `add_option`（既存があれば no-op）で行い、**以後のアップデートで書き換えない**。バージョンアップのたびに基準日がリセットされると棚卸しが永久に発動しなくなる
- 判定は毎回**その時点の設定値**を読む。既定値は判定に一切登場しない（設定を変えれば即座に反映される）

**テスト必須項目**: 「有効化したままアップグレードしたサイトで基準日が作成されること」と「既に基準日があるサイトでアップグレードしても上書きされないこと」の 2 つ。前者は activation hook に頼った実装では落ちる。

### 5-4. 設定項目

`GeneralSettings::DEFAULTS` に追加する。`all()` が DEFAULTS をベースに保存値をマージする実装のため、新キーを足しても**既存サイトの保存値は保たれる**。

| キー | 型 | 既定値 | 説明 |
| --- | --- | --- | --- |
| `stocktake_enabled` | bool | **true** | 棚卸しの有効/無効 |
| `stocktake_days` | int（1 以上） | **180** | 最終掲載日からこの日数を過ぎたら更新対象から外す |

**`stocktake_days` は保存時に 1 以上へクランプする**（既存の `queue_depth_cap` / `retention_*` と同じ `max(1, (int) $value)` の扱いに揃える）。0 や負数を許すと基準日と現在時刻の比較が常に真になり、**全商品が即座に棚卸しされて価格が一斉に消える**。0 を「無効化」の意味に使う設計は採らない。無効化は `stocktake_enabled` が担うため、値の意味を二重化しない。

**`stocktake_enabled` を既定 true とする理由**: 「更新不要な商品の API を叩かない」はプラグインの標準挙動として正しく、既定 false では大半の利用者が有効化しないまま無駄な呼び出しを続けることになる。既存サイトにとっても、棚卸し基準日＋180 日の猶予があるためアップデート直後に挙動が変わることはない。無効化したい利用者は設定から切れる。

#### 既定値 180 日の根拠

- コンテンツの可視性の半減期は、競争の激しい領域で 12〜18 ヶ月から **3〜6 ヶ月**へ短縮している（技術系は 60〜90 日）
- 大半の記事は更新なしで **6〜12 ヶ月**後に検索順位を失い始める
- アフィリエイト実務では「**半年に 1 回、最低でも年に 1 回**は掲載情報を見直す」のが目安とされる

180 日を採る理由は 3 つある。第一に、流入の半減期が 3〜6 ヶ月なので 6 ヶ月経過は「ほぼ読まれなくなった」と判断してよい。第二に、**アフィリエイト実務の見直し周期と一致するため、通常運用でリライトすれば掲載日が更新されて棚卸しされない**。対象になるのは「半年間一度も手を入れていない＝実質的に放棄された記事」だけになる。第三に、誤棚卸しのコスト（価格が消える）に対して安全側である。90 日は攻めすぎで、まだ流入がある記事を切ってしまう。

出典: [Content Decay in 2026](https://wordpattern.org/blogs/why-your-best-posts-are-losing-traffic/) / [What Is Content Decay?（Neil Patel）](https://neilpatel.com/blog/content-decay/) / [Your Best Blog Post Has a 90-Day Shelf Life Now](https://www.averi.ai/how-to/your-best-blog-post-has-a-90-day-shelf-life-now) / [ドコモ アフィリエイト｜記事のリライト方法](https://affiliate.docomo.ne.jp/statics/guide/news02_046)

### 5-5. 適用箇所

| 経路 | 棚卸しの適用 |
| --- | --- |
| `QueueMaintenance::sweep()`（継続更新） | **適用**（対象をスキップ） |
| `PublishTrigger`（記事の公開・更新） | 適用しない（このとき掲載日が更新されるため、そもそも対象にならない） |
| 手動更新 / 強制更新（管理画面ボタン・REST） | **適用しない**（明示操作は常に実行する） |

### 5-6. 棚卸し後の挙動

更新が止まると 24 時間で `PriceFreshness::isPriceDisplayable()` が false になり、**カードから価格が消える**。カード本体・書影・CTA リンクは従来どおり描画され、アフィリエイト導線は維持される。これを既定の挙動として受け入れる。

### 5-7. 復活経路

- **記事を再保存する**（最終掲載日が更新され、対象へ戻る）
- **棚卸し期間を延ばす**（§5-2 のとおり状態を持たないため即座に戻る）

商品ごとの個別「棚卸し除外」フラグは**今回は設けない**。既定値を半年に置けば通常のリライト運用で自然に復活するため、設定項目を増やす割に使われない可能性が高い。実際に困った時点で追加を検討する。

### 5-8. 商品一覧の表示

- **「最終掲載日」列を追加**する（「最終同期」列の隣）
- この列を**ソート可能にする**（`manage_edit-affilicard_product_sortable_columns` ＋ `pre_get_posts` の meta ソート）。棚卸し状況を一覧で把握する唯一の導線となるため必須
- 棚卸し対象の商品は視覚的に区別できるようにする

**「最終同期」列のソートはスコープ外とする。** 最終同期の値は listing の JSON 配列内にあり、meta ソートに乗せるには派生 meta の追加と既存 926 商品のマイグレーションが必要で、得られるものが並べ替えだけであるため割に合わない。

## 6. データモデル

### 6-1. 新規 post meta

| キー | 型 | 説明 |
| --- | --- | --- |
| `affilicard_last_published_at` | string（ISO8601・UTC） | 最終掲載日。ISO8601 は辞書順＝時系列順のため meta_value の文字列ソートで正しく並ぶ |

**read-only とする。** `register_post_meta()` の `auth_callback` で編集を拒否し、REST でも読み取りのみとする。利用者が直接編集すると棚卸し判定が意図せず変わるため。

| --- | --- | --- |
| `affilicard_stocktake_baseline` | string（ISO8601・UTC） | 棚卸し基準日。初回有効化時に `add_option` で 1 度だけ記録 |
| `affilicard_last_sweep_completed_at` | string（ISO8601・UTC） | 最後に sweep が完走した時刻（§4-4） |

## 7. テスト方針

外部 API（楽天 / DMM）・Action Scheduler・WP のフックはすべてモックする。

#### 供給側

- バッチハンドラがレート間隔を守って順次 fetch すること
- 残り時間が閾値を切ったとき、未処理分を新ジョブとして積み直して終了すること
- **待機に入る前に期限を確認すること**（待機中に期限超過して残りが失われないこと）
- **レート待ちが残り時間でクランプされること**
- `TRANSIENT_FAILURE` の listing が per-listing ジョブへ落ちること
- `TERMINAL_FAILURE` で give-up マーカーが立ち、per-listing へ落ちないこと
- pause 中にジョブが失われないこと（既存の温存挙動の回帰）
- `enqueueSweep()` が unique 重複時に depthMemo を進めないこと
- **継続ジョブの投入に失敗してもカーソルが残り、次回 sweep が途中から再開できること**
- sweep のカーソル分割が全商品を漏れなく走査すること
- **`queue_depth_cap` 到達時にカーソルが保持され、次の sweep が続きから積むこと**

#### 需要側

- 判定式の境界値（ちょうど期間経過の日、1 日前、1 日後）
- 最終掲載日が **null / 空文字 / パース不能**のいずれでも基準日にフォールバックすること
- **有効化したままアップグレードしたサイトで基準日が作成されること**（activation hook 依存では落ちる）
- **基準日が既にある場合、アップグレードで上書きされないこと**
- **`stocktake_days` が 0 / 負数で保存されたとき 1 以上へクランプされること**
- 設定期間を延ばすと対象が復帰すること
- 手動更新・強制更新が棚卸しの影響を受けないこと
- 記事の公開・更新で最終掲載日が更新されること
- **既存値より古い時刻では上書きされないこと**（単調増加）
- 最終掲載日 meta が REST / 編集画面から書き換えられないこと
- 商品一覧の meta ソートが機能すること

## 8. 実装後に再評価する項目

設計上の判断は済んでいるが、実測値を見て見直す余地があるもの。

1. **per-listing フォールバック時の RateLimiter 挙動** — 本 spec では従来どおり再投入とする（§4-1）。異常系は少数という前提に立っているが、実装後の実測で空振りが目立つようならバッチと同じ待機方式へ揃える。
2. **バッチサイズの安全マージン** — time limit 30 秒に対し 25 秒で打ち切る想定（§4-1）。実環境の fetch 所要時間を測って調整する。
3. **`stocktake_days` の既定値** — 180 日は業界一般の指標に基づく推定値（§5-4）。運用データが蓄積したら実際の流入減衰カーブで検証する。

## 9. スコープ外

| 項目 | 理由 |
| --- | --- |
| 閲覧駆動リフレッシュ | 原設計 §10-1 の判断を維持（§5-1 で代替手段を採用） |
| GA4 等の外部分析基盤との連携 | 利用者の計測環境に依存し、汎用プラグインとして不適 |
| orphan（未参照商品）の除外 | 実測で削減余地 0.9%。作り込む価値が薄い |
| 「最終同期」列のソート | 派生 meta の追加とマイグレーションが必要で割に合わない（§5-8） |
| multi-item API バッチ（Amazon GetItems 等） | 原設計 §7-2 #10 の後回し最適化のまま。楽天は keyword 単位のため対象外 |
| サーバー cron の自動設定 | プラグインからサーバーの crontab は操作できない。ドキュメントと健全性検出で対応（§4-4） |

## 10. 移行と後方互換

- 新 meta / option の追加のみで、既存の meta・設定・スケジュール済みアクションは変更しない
- 既存の pending な `affilicard_refresh_listing` ジョブは従来どおり処理される（バッチジョブと共存する）
- 棚卸しは最終掲載日が空の商品でも基準日で判定できるため、**マイグレーション用の一括スキャンは不要**
- 公開 IF の破壊的変更は無いため **MINOR（v3.5.0）** とする
